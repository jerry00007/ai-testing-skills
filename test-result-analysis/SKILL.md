# 测试结果分析（证据驱动）

## 为什么需要这个 skill

AI 在分析测试结果时最容易犯三类错：

1. **主观代替客观**——"理论上没问题""应该能过"，但不跑实际命令
2. **甩锅历史遗留**——"这个失败是之前就有的"，但拿不出前后对比证据
3. **结论无证据链**——"测试通过"，但不贴 exit code、不贴失败数、不贴输出片段

这三个毛病的根源是一样的：**没有把"判定"建立在可复现的证据上**。

本 skill 的作用：在分析测试结果/日志/验证结论时，强制走一套**证据驱动**的流程，让结论可追溯、可复验、无法糊弄。

> 与 `verification-before-completion` 的分工：那个是"声称完成前必须验证"的**通用纪律**；本 skill 是"测试结果分析"场景的**专项方法论**，额外提供基线对比、增量归因、结构化结论模板。

---

## 核心原则

| 原则 | 含义 | 反例（禁止） |
|---|---|---|
| **证据先行** | 结论必须基于实际运行的命令输出，不是推理 | "代码逻辑上没问题，应该能过" |
| **基线对比** | 涉及代码改动时，必须有改动前后的状态对比 | 只看改动后状态，直接下结论 |
| **增量归因** | 每个失败/错误必须明确：本次引入 or 历史遗留 or 环境问题 | "测试失败，可能是历史问题" |
| **客观判定** | pass/fail 由数据说话（exit code / 失败数 / 错误数），不主观 | "大部分通过，整体看起来还行" |
| **完整呈现** | 关键证据要贴出来，不是"我看了，没问题" | "我检查了日志，没有异常" |

## 执行流程（The Analysis Gate）

分析测试结果时，按此顺序执行，**每一步都不能跳**：

### Step 1: 明确分析对象
先搞清楚用户要你分析的是什么：
- 跑测试看结果？→ 需要先执行测试命令
- 分析已有的测试报告/日志文件？→ 需要先读取文件
- 验证某个改动是否破坏了什么？→ 需要基线 + 当前对比
- 诊断某个具体报错？→ 需要定位错误来源

**不要假设**——如果用户说的不清楚，先问清楚再动手。

### Step 2: 收集原始证据
**实际运行命令或读取文件**，拿到原始输出。禁止凭记忆/推理下结论。

| 场景 | 该做什么 | 不该做什么 |
|---|---|---|
| 测试结果 | 运行测试命令，捕获完整输出 + exit code | "我记得上次是通过的" |
| 日志分析 | 读取日志文件，grep 关键错误模式 | "日志我扫了一眼" |
| Lint/类型检查 | 运行 `lsp_diagnostics` 或对应 linter | "代码看起来没有类型问题" |
| 构建结果 | 运行构建命令，看 exit code | "编译应该没问题" |

**证据保存**：关键输出片段要保留（exit code、失败数、错误行、stack trace 关键帧），写进结论里。

### Step 3: 建立基线（涉及代码改动时必需）
如果是验证"某次改动"的影响，**必须**有基线：

- **改动前**：运行一次测试/diagnostics，snapshot 当前状态（通过数、失败数、warning 数、错误列表）
- **改动后**：再运行一次，snapshot 新状态
- **对比**：新增了什么失败？消失了什么失败？数量怎么变？

> 如果用户没提供基线，且改动已经发生无法回溯，**明确说"无法做增量归因，以下结论基于当前状态而非增量"**，不要假装做了对比。

### Step 4: 增量归因（对每个失败/错误）
对每一个失败项，必须回答：**这个失败是哪来的？**

| 归因类别 | 判定依据 | 结论措辞 |
|---|---|---|
| **本次引入** | 基线中不存在，改动后新增 | "由本次改动引入，必须修复" |
| **历史遗留** | 基线中已存在，改动后仍在 | "改动前已存在，本次未引入，但建议修复" |
| **环境/数据问题** | 与代码逻辑无关（如依赖缺失、端口占用、测试数据脏） | "环境问题导致，非代码缺陷" |
| **不确定** | 无基线可对比，无法判定 | "无法判定来源，需补充基线" |

**禁止**把不确定的归为"历史遗留"——这是最典型的偷懒。无基线就明说无基线。

### Step 5: 输出结构化结论
用固定模板输出，**不要自由发挥**。模板见下节。

---

## 结论输出模板

分析完必须给出结构化结论，格式如下：

```
## 测试结果分析

### 执行的命令
[列出实际运行的所有命令，含完整参数]

### 总体结论
[PASS / FAIL / PARTIAL] —— 一句话结论

### 证据
- exit code: [实际值]
- 通过/失败: [如 34 passed, 2 failed]
- 关键输出片段:
  ```
  [贴失败测试的报错、stack trace 关键行、或确认通过的输出尾部]
  ```

### 失败项归因（如有失败）
| 失败项 | 归因 | 依据 |
|---|---|---|
| [测试名/错误] | 本次引入/历史遗留/环境/不确定 | [对比基线的具体证据] |

### 建议动作
- [必须修复的：xxx]
- [建议修复的：xxx]
- [无需处理的：xxx]
```

**关键纪律**：
- "总体结论"必须是 PASS/FAIL/PARTIAL 三选一，禁止"基本通过""大体没问题"这种模糊措辞
- "证据"段必须贴实际输出，不能只说"我看了"
- "失败项归因"段，每个失败都要有归因，不能只列失败不归因

## 日志分析的专项策略

分析日志（非测试结果）时，Step 2 的证据收集用这套策略：

1. **先定位错误级别**：grep `ERROR|FATAL|Exception|Traceback|panic` 等关键模式
2. **提取时间线**：错误发生的时间戳、第一个错误出现的位置
3. **追溯根因**：从第一个错误往前看上下文（通常根因在第一个错误之前），不要只看最后一行
4. **过滤噪音**：区分 signal vs noise——重复的 warning 可能是噪音，但首次出现的 error 通常是 signal
5. **关联上下文**：错误发生时系统在做什么？（哪个请求、哪个任务、哪个用户操作）

**输出时**：贴关键错误行 + 时间戳 + 你推断的根因，而不是"日志里有几个错误"。

---

## 常见偷懒模式（Red Flags）

发现自己有以下念头时，**停下来**，回到 Step 2 重新收集证据：

| 念头 | 真相 |
|---|---|
| "这个失败应该是历史问题" | 没有基线对比，你不能说"应该"——去查 |
| "代码逻辑上没问题" | 逻辑判断 ≠ 实际运行结果——去跑 |
| "我只看了最后几行，没异常" | 错误可能在中段——全量扫 |
| "测试通过了" | 贴 exit code 和通过数，不是一句话 |
| "这个报错和上次一样" | 贴这次的 stack trace，证明它和上次一样 |
| "改动很小，不会影响测试" | 跑了才知道——跑 |
| "大部分通过" | PARTIAL 不是"基本 OK"，明确有几个失败 |
| "环境问题，不是代码问题" | 证明是环境问题（缺什么依赖、什么端口占用），不是猜 |

## 为什么这样设计（The Why）

这套流程背后的核心信念来自 Harness Engineering 的一个洞察：

> **Rule 会软，Skill 是步骤，Scripts 是裁判。** 完成定义必须从主观变客观——AI 说做完了没用，得跑过证据这关才算。

具体到测试结果分析：
- **基线对比**存在的意义：堵死"历史遗留"这个万能借口。没有基线，AI 永远可以把失败甩给"之前就这样"。
- **增量归因**存在的意义：让每个失败都有明确责任归属，强迫区分"我搞坏的"vs"本来就坏的"。
- **结构化结论**存在的意义：让结论可审计。事后任何人看到结论，都知道当时基于什么证据、归因怎么来的。

这不是形式主义——这是让"测试通过"从一句话，变成一个**可复验的事实**。

---

## 何时不需要完整流程

以下情况可以简化（但仍需证据）：
- 用户只是快速问"测试大概什么状态"→ 跑命令贴结果，无需完整模板
- 单个文件的 typo 修复→ 跑该文件相关测试即可，无需全量基线
- 纯查询（"现在有几个 failing test"）→ 直接跑命令回答

判断标准：**用户要的是"结论"还是"数据"**。要结论→走完整流程；要数据→直接给数据。但无论如何，**不能凭推理代替实际运行**。
