# 三视角检查清单 (Three-Perspective Checklists)

## 产品专家 (Visionary) — "做正确的事"

### 业务逻辑完整性

- [ ] 核心业务流程是否有缺失环节？
- [ ] 是否存在循环依赖或死锁的业务流程？
- [ ] 状态机转换是否完整（每个状态的入口和出口）？
- [ ] 是否存在不可逆操作但缺少确认步骤？
- [ ] 权限模型是否覆盖所有操作场景？
- [ ] 边界用户（新用户/冷启动/注销用户）的处理是否定义？

### 用户体验闭环

- [ ] 操作反馈是否及时且明确？
- [ ] 错误信息是否可理解（非技术用户视角）？
- [ ] 加载/等待状态是否有适当提示？
- [ ] 是否存在用户可能困惑的操作路径？
- [ ] 空状态（无数据）页面是否设计？

### 功能边界清晰度

- [ ] MVP 范围是否明确（做什么、不做什么）？
- [ ] 是否存在模糊描述（"尽可能"、"合适时"、"根据情况"）？
- [ ] 数据生命周期管理（创建、更新、归档、删除）是否定义？
- [ ] 数据权限隔离是否考虑？
- [ ] 版本兼容/灰度/回滚策略是否提及？

### 业务指标可度量性

- [ ] 成功标准是否可量化（不是"提升用户体验"而是"CTR提升≥5%"）？
- [ ] 是否有明确的 AB 实验设计（对照组、实验组、流量分配）？
- [ ] 核心指标的定义是否明确（分子/分母/统计口径）？
- [ ] 是否有负面指标定义（如"探索不能降低整体CTR超过X%"）？

## 架构师 (Builder) — "正确地做事"

### 技术可行性

- [ ] 需求是否超出当前系统架构能力？需要什么基建？
- [ ] 新增概念是否与现有系统概念冲突或重叠？
- [ ] 是否需要新的数据源/数据流？数据从哪里来？
- [ ] 是否需要新的接口/服务？与现有服务如何集成？
- [ ] 离线/近线/在线的计算分工是否明确？

### 性能与扩展性

- [ ] 预估 QPS / 数据量 / 响应时间是否在合理范围？
- [ ] 是否存在 N+1 查询或同步阻塞？
- [ ] 热点数据是否有缓存层？缓存策略是否合理？
- [ ] 大数据量场景是否有分页/流式处理？
- [ ] 如果业务量增长 10 倍，哪些环节先崩溃？

### 集成影响

- [ ] 新功能对现有模块的影响链路是什么？
- [ ] 是否需要修改现有接口？是否向后兼容？
- [ ] 数据迁移方案是否设计？
- [ ] 配置变更是否支持灰度/回滚？
- [ ] 上下游依赖（数据生产方/消费方）是否同步？

### 数据一致性

- [ ] 缓存、数据库、消息队列之间的一致性方案是否设计？
- [ ] 是否存在并发写入冲突？冲突检测机制是什么？
- [ ] 分布式场景下是否需要分布式锁？
- [ ] 事务边界是否合理？是否需要分布式事务？
- [ ] 数据回滚/补偿机制是否设计？

### 安全与权限

- [ ] 认证授权机制是否完善？
- [ ] 敏感数据是否加密存储和传输？
- [ ] 是否存在注入/XSS/CSRF 风险？
- [ ] API 速率限制是否合理？
- [ ] 日志是否泄露敏感信息？

---

## 测试专家 (Gatekeeper) — "把事做对"

### 可测试性

- [ ] 验收标准是否可量化为 PASS/FAIL？
- [ ] 每个 PRD 声明是否可以映射到具体的测试步骤？
- [ ] 测试数据准备是否可行？（数据从哪来、格式是什么）
- [ ] 是否有可用的测试环境/工具/基建？
- [ ] 核心指标是否可埋点/可统计？

### 边界条件覆盖

- [ ] 空数据/零值/负值处理是否定义？
- [ ] 极大值/极小值场景是否考虑？
- [ ] 时区/时间边界（跨日/跨月/跨年）是否处理？
- [ ] 网络中断/弱网/超时场景是否设计？
- [ ] 编码问题（Unicode/特殊字符）是否考虑？

### 幂等与重试

- [ ] 重复操作（用户多次点击、消息重投）是否幂等？
- [ ] 网络重试/回调重试是否有处理？
- [ ] 第三方服务超时/失败时的降级策略是否设计？
- [ ] 优雅降级策略是否完善（核心功能可用、非核心降级）？

### 兼容与回归

- [ ] 对现有功能的影响测试是否规划？
- [ ] 是否需要回归测试 1.0 / 旧版本功能？
- [ ] AB 实验切换期间，新旧逻辑是否兼容？
- [ ] 灰度发布策略是否可测试？

### 监控与告警

- [ ] 关键业务指标监控是否设计？
- [ ] 异常告警阈值是否合理？
- [ ] 是否有降级开关/熔断机制？
- [ ] 日志埋点是否覆盖关键链路？
- [ ] 是否有数据质量监控（如产出数据完整性校验）？

## 优先级判定标准

| 优先级 | 定义 | 判定条件 |
|--------|------|---------|
| **P0** | 阻塞开发 | 不确认则无法启动技术方案设计；架构方向不确定；数据源/接口未定义 |
| **P1** | 影响质量 | 不确认会导致返工或质量风险；参数缺失会影响核心功能；边界条件不明确 |
| **P2** | 建议明确 | 不确认可以开发，但建议产品在开发期间明确；非核心路径的细节 |

### P0 数量校准

- P0 问题 ≤ 3 个: 正常，需求基本可执行
- P0 问题 4-7 个: 需求不够成熟，建议产品补充后再启动
- P0 问题 > 7 个: 需求不成熟，建议退回产品重新评审
