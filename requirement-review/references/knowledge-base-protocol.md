# 知识库交叉验证协议 (Knowledge Base Cross-Reference Protocol)

## 目标

在开始三视角专家分析前，先用已有知识库解答尽可能多的 PRD 问题。
经验表明，50%-70% 的评审问题可以通过代码库和文档自行解答。

---

## 执行步骤

### Step 1: PRD 解构

逐段阅读 PRD 文档，提取所有"隐含问题"：

**关注点类型:**

| 类型 | 示例 | 为什么要提取 |
|------|------|-------------|
| 模糊术语 | "非明文召回"、"探出n个"、"打散" | 术语可能有代码级含义 |
| 未明确参数 | 阈值、频率、数量限制、超时时间 | 代码中可能有默认值 |
| 缺失边界条件 | 空数据、并发、失败兜底 | 1.0 可能已有处理逻辑 |
| 新增概念 | PRD 引入的 1.0 没有的概念 | 需确认是真正的新概念还是已有概念换了个名字 |
| 流程描述 | "先做A再做B"、"如果X则Y" | 代码中可能已有实现 |
| 数据格式 | "输入"、"输出"、"迁移结果" | 可能有已有数据结构 |

**提取格式:**

```
[问题编号] PRD原文: "..." (§章节名)
隐含问题: 术语X的具体含义是什么？参数Y的值是多少？
```

### Step 2: 知识库扫描

针对每个隐含问题，在以下位置搜索：

**优先搜索路径 (按顺序):**

1. **代码知识库**: `doc/` 目录下的架构和代码文档
   - 搜索关键词：术语名、参数名、接口名、配置项名
   - 关注：章节标题、代码示例、配置说明

2. **测试经验**: `test_cases/` 目录下的测试配置和经验沉淀
   - 搜索关键词：术语名、参数名、bug 描述
   - 关注：exp_info.py 中的配置参数、测试点矩阵中的验证点、问题沉淀中的踩坑

3. **业务文档**: 项目根目录或 `doc/` 下的业务逻辑文档
   - 搜索关键词：业务术语、流程名
   - 关注：业务流程描述、状态机、数据流

4. **源代码** (如果知识库不够):
   - 使用 grep 搜索代码中的参数名、配置项
   - 关注：配置文件、常量定义、接口签名

**搜索策略:**

- 先搜术语的精确匹配
- 如果无结果，搜术语的部分匹配
- 如果仍无结果，搜相关功能模块名
- 如果还是无结果，标记为"需确认"

### Step 3: 三分类

对每个隐含问题进行分类：

#### ✅ 已自解 (Self-Resolved)

条件（ALL 必须满足）:
- 知识库中有明确的、无歧义的答案
- 答案来源可追溯到具体文件和章节
- 答案与 PRD 描述不矛盾

记录格式:
```
✅ [编号] 问题: "术语X的含义"
   结论: X = Y（具体定义）
   来源: doc/xxx.md §章节名
   备注: （如有补充说明）
```

#### 🟡 部分自解 (Partially Resolved)

条件（满足任一）:
- 知识库中有相关上下文，但缺少最终参数确认
- 知识库中有 1.0 的实现，但 2.0 可能有变化
- 知识库中有间接证据，需要产品确认是否适用

记录格式:
```
🟡 [编号] 问题: "参数X的值"
   已知: 1.0中X=10（来源: exp_info.py L行号）
   待确认: 2.0是否沿用相同值？
```

#### 🔴 需确认 (Needs Confirmation)

条件（满足任一）:
- 知识库中完全无对应信息
- 是纯业务决策（如准确度阈值、ROI 判断）
- 是新增概念，1.0 代码中无实现
- 多个知识库来源给出矛盾答案

记录格式:
```
🔴 [编号] 问题: "迁移算法选型"
   原因: 1.0代码中无"迁移"概念，是全新能力
   需确认: 迁移用什么算法实现？
```

### Step 4: 输出自解清单

汇总所有分类结果，输出表格:

```
| # | 问题 | 分类 | 结论/待确认 | 来源/原因 |
|---|------|------|------------|----------|
| 1 | 术语X | ✅自解 | X=Y | doc/xxx.md §3 |
| 2 | 参数Y | 🟡部分 | 1.0中Y=10 | exp_info.py |
| 3 | 算法Z | 🔴需确认 | 无代码实现 | 全新概念 |
```

---

## 自解率校准

| 自解率 | 诊断 | 行动 |
|--------|------|------|
| 70%+ | 知识库覆盖良好 | 正常继续 |
| 40%-70% | 正常范围 | 正常继续 |
| 20%-40% | 知识库可能不完整 | 检查是否遗漏了知识库文档 |
| <20% | 可能知识库扫描不充分 | STOP，补充扫描或确认知识库是否覆盖该需求领域 |

**注意**: 自解率也与 PRD 质量有关。如果 PRD 非常模糊，自解率可能偏低（因为连问题都提取不出来）。如果 PRD 非常详细，自解率也可能偏低（因为产品已经把细节写清楚了，不需要查代码）。

## 常见知识库文档清单

推荐的项目知识库结构（如果项目缺少这些，建议补充）:

```
doc/
├── engine代码知识库.md           # 引擎架构、处理链路、配置项
├── recall代码知识库.md           # 召回架构、召回类型、合并逻辑
├── 推荐系统业务逻辑完整文档.md    # 业务流程、数据流、状态机
├── 点后推召回知识库.md           # 点后推专题知识
└── 兴趣探索1.0-测试踩坑与经验沉淀.md  # 经验沉淀

test_cases/
└── [feature_name]/
    ├── exp_info.py               # 实验配置、ACM参数、阈值
    ├── 测试点矩阵-[feature].md    # 系统化的测试点清单
    └── 问题沉淀-[feature].md      # 已知bug和踩坑记录
```
