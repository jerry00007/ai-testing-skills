# 需求评审 (Requirement Review)

基于知识库交叉验证 + 三剑客多视角分析的 PRD 评审框架。
先自查、再提问，输出产品经理可直接使用的反馈文档。

---

## 执行铁律 (MANDATORY RULES)

1. **Phase 0 不可跳过**: 必须先扫描知识库再开始专家分析，不得直接跳到三角色评审
2. **自解优先**: 凡是知识库/代码能回答的问题，不得转交给产品确认
3. **证据驱动**: 每个自解结论必须标注来源（文件路径 + 章节号/行号）
4. **P0/P1/P2 分类强制**: 所有需产品确认的问题必须有优先级标签
5. **输出必须可执行**: 反馈文档必须包含具体问题 + 上下文 + 建议方案，禁止泛泛而谈
6. **角色独立**: 三个专家角色必须独立分析，不允许相互妥协
7. **红蓝对抗不可跳过**: Phase 2 是核心质量保证环节

---

## 禁止行为 (PROHIBITED)

- MUST NOT 跳过 Phase 0 知识库扫描
- MUST NOT 将已能在代码/文档中找到答案的问题转交给产品
- MUST NOT 使用泛泛而谈的表述（"建议优化"、"注意性能"、"可能有问题"）
- MUST NOT 产出不带证据来源的自解结论
- MUST NOT 遗漏优先级分类（P0/P1/P2）
- MUST NOT 在红蓝对抗中识别少于 3 个真实问题
- MUST NOT 输出超过用户指定范围的评审内容

---

## 执行流程

严格按五个阶段执行，每阶段有强制 checkpoint。

### 输入收集

接收 PRD 文档路径，读取文档内容。

识别评审范围：
- 如果用户指定了范围（如"重点关注引擎和召回"），以此为边界
- 如果未指定，覆盖 PRD 全部内容
- 记录范围声明，后续分析不得超出边界

识别知识库位置：
- 检查项目 `doc/` 目录下的知识文档
- 检查 `test_cases/` 目录下的测试配置和经验沉淀
- 检查项目根目录下的架构文档
- 如果用户指定了知识库路径，以用户指定为准

---

### Phase 0: 知识库交叉验证 (Knowledge Base Cross-Reference)

**这是本技能的核心差异化环节。**

目标：在开始专家分析前，先用已有知识库解答尽可能多的 PRD 问题，减少需要产品确认的问题数量。

详细协议见 `references/knowledge-base-protocol.md`。

执行步骤：

1. **PRD 解构**: 逐段阅读 PRD，提取所有"隐含问题"（每个描述模糊的术语、每个未明确的参数、每个缺失的边界条件）
2. **知识库扫描**: 针对每个隐含问题，在知识库中搜索对应答案
3. **三分类**: 将每个问题标记为：
   - ✅ **已自解**: 知识库中有明确答案，标注来源
   - 🟡 **部分自解**: 知识库中有相关上下文，但缺少最终确认
   - 🔴 **需确认**: 知识库中无对应信息，必须产品确认
4. **输出自解清单**: 列出所有已自解的问题 + 证据

#### ⛔ CHECKPOINT: Phase 0 Complete?

- [ ] 是否已扫描全部相关知识库文档？
- [ ] 每个自解结论是否标注了来源（文件路径 + 章节/行号）？
- [ ] 三分类是否完整（已自解 / 部分自解 / 需确认）？
- [ ] 自解率是否合理？（通常 40%-70%，过高可能漏读PRD，过低可能漏扫知识库）

**如果自解率 < 20%，STOP 并补充知识库扫描后再继续。**

---

### Phase 1: 三视角专家分析 (Three-Perspective Analysis)

三个专家角色分别分析 **Phase 0 未自解的问题**。每个角色独立产出结论。

详细检查清单见 `references/perspective-checklists.md`。

#### 角色 1: 产品专家 (Visionary)

关注"做正确的事"。分析维度：

- **业务逻辑完整性**: 核心流程是否有缺失环节？状态机是否完整？
- **用户体验闭环**: 操作反馈是否及时？错误信息是否可理解？
- **功能边界清晰度**: MVP范围是否明确？模糊描述是否存在？
- **数据生命周期**: 创建、更新、归档、删除流程是否定义？
- **业务指标可度量性**: 成功标准是否可量化？

#### 角色 2: 架构师 (Builder)

关注"正确地做事"。分析维度：

- **技术可行性**: 需求是否超出当前系统架构能力？需要什么基建？
- **性能与扩展性**: 预估QPS、数据量、响应时间是否在合理范围？
- **集成影响**: 新功能对现有模块的影响链路是什么？
- **数据一致性**: 缓存、数据库、消息队列之间的一致性方案是否设计？
- **安全与权限**: 认证授权、数据隔离、敏感信息保护是否覆盖？

#### 角色 3: 测试专家 (Gatekeeper)

关注"把事做对"。分析维度：

- **可测试性**: 验收标准是否可量化为 PASS/FAIL？
- **边界条件覆盖**: 空数据、极值、并发、异常输入是否考虑？
- **幂等与重试**: 重复操作、网络重试、回调是否处理？
- **兼容与回归**: 对现有功能的影响测试是否规划？
- **监控与告警**: 关键指标监控、异常告警是否设计？

#### 输出格式

每个角色对每个待分析问题产出：

```
### 问题 [编号]: [问题标题]
- 角色视角: [产品/架构/测试]
- 分析结论: [具体的技术/业务判断]
- 依据: [代码证据 / 架构原理 / 测试经验 / 业务逻辑]
- 建议: [具体的修复/确认/补充方案]
- 优先级: [P0/P1/P2]
```

#### ⛔ CHECKPOINT: Phase 1 Complete?

- [ ] 每个角色是否覆盖了所有 Phase 0 未自解的问题？
- [ ] 每个分析是否包含具体技术细节（禁止泛泛而谈）？
- [ ] 每个分析是否标注了优先级（P0/P1/P2）？
- [ ] 角色之间是否独立分析（不允许妥协）？

---

### Phase 2: 红蓝对抗 (Adversarial Cross-Check)

对 Phase 1 的结论进行攻击性审查。必须识别至少 3 个真实风险。

攻击方向：

- **QA → PM**: 业务流程漏洞、用户操作边界、ROI 质疑
- **QA → Architect**: 性能瓶颈、故障场景、数据一致性
- **Architect → PM**: 技术复杂度质疑、方案简化建议、基建依赖

每个攻击必须包含：
- 具体攻击场景（可复现的操作步骤或系统条件）
- 发现的问题（具体的技术/逻辑缺陷）
- 影响范围（影响多少用户/数据/业务流程）
- 严重程度评级（🔴高/🟡中/🟢低）

#### ⛔ CHECKPOINT: Phase 2 Complete?

- [ ] 至少识别 3 个真实风险？
- [ ] 每个风险是否有具体攻击场景（非泛泛而谈）？
- [ ] 是否覆盖了 QA→PM、QA→Architect、Architect→PM 三个方向？
- [ ] 每个风险是否有严重程度评级？

---

### Phase 3: 收口与优先级排序 (Synthesis & Prioritization)

合并 Phase 0-2 的所有发现，按优先级排序，生成最终反馈清单。

分类规则：

- **P0 — 阻塞开发**: 不确认则无法启动技术方案设计
- **P1 — 影响质量**: 不确认会导致返工或质量风险
- **P2 — 建议明确**: 不确认可以开发，但建议产品在开发期间明确

合并规则：
- 同一问题被多个角色提到的 → 合并为一条，保留最严重的优先级
- Phase 0 已自解的问题 → 列入"已自解清单"，仅告知产品
- Phase 2 红蓝对抗发现的 **新问题** → 追加到需确认清单

---

### Phase 4: 输出反馈文档 (Output Generation)

生成产品经理可直接使用的反馈文档。

详细输出模板见 `references/output-template.md`。

输出包含：

1. **摘要**: 自解率统计、需确认问题数、P0/P1/P2 分布
2. **已自解清单**（仅告知）: 问题 + 结论 + 证据来源
3. **需产品确认清单**（核心）:
   - P0 问题: 问题 + 为什么知识库答不了 + 需确认什么 + 建议
   - P1 问题: 同上 + 已知上下文
   - P2 问题: 同上
4. **红蓝对抗风险摘要**: 风险 + 影响 + 建议

格式要求：
- 默认输出 Markdown + DOCX 双格式
- 中文
- 结构化表格优先
- 每个问题自包含（产品不需要翻看其他文档即可理解）

#### ⛔ CHECKPOINT: Phase 4 Complete?

- [ ] 反馈文档是否包含"已自解清单"和"需确认清单"两部分？
- [ ] 每个需确认问题是否标注了"为什么知识库答不了"？
- [ ] 每个需确认问题是否有具体的"需确认什么"？
- [ ] P0/P1/P2 分类是否清晰？
- [ ] 文档是否可以直接发送给产品经理（无需技术术语解释）？

---

## 适配场景

- 新功能 PRD 评审（输入 docx/md/pdf）
- 技术方案评审（输入设计文档）
- 需求变更评审（输入变更说明 + 原 PRD）
- 上线前风险评估（输入 PRD + 测试报告）

## 输出校准

- Phase 0 自解清单: 通常 5-15 个条目
- Phase 1 三视角分析: 每个角色 3-8 个发现
- Phase 2 红蓝对抗: 3-10 个真实风险
- Phase 4 最终输出: 通常精简到 5-15 个需确认问题（自解率 40%-70%）
- 如果最终需确认问题 > 20 个，考虑是否知识库扫描不充分

## 关键原则

1. **减少产品负担**: 能自己查到的答案不麻烦产品
2. **证据驱动**: 每个结论都有来源
3. **结构化输出**: 产品能直接看懂、直接回复
4. **聚焦核心**: P0 问题不超过 5 个，否则说明需求本身不成熟
