# Code Review — 企业级代码审查框架

> **核心理念**：Review 的目标不是找尽所有理论问题，而是**准确识别真正影响生产的实际问题**。
> 过度报警（P0 虚高）比漏报更危险——它会浪费开发时间并削弱对 review 结论的信任。

---

## 执行铁律 (MANDATORY RULES)

1. **每个发现必须引用具体代码位置**（文件名 + 行号），禁止笼统说"这段代码可能有问题"
2. **每个 P0/P1 发现必须包含完整执行路径追踪**（输入 → 处理 → 输出 → 失败点）
3. **定级校准是不可跳过的核心环节** — Phase 3 对每个发现进行质疑，不通过的自动降级
4. **禁止纯理论问题** — 如果无法构造一个真实的触发场景，不得定为 P1 及以上
5. **禁止定级通胀** — 宁可漏报一个 P2，不可虚报一个 P0
6. **必须给出明确的提测/发布决策**：✅ 可以提测 / ⚠️ 修复后提测 / ❌ 阻断提测
7. **需求追溯矩阵（RTM）是必查项** — Phase 0.5 必须逐条对照需求原文与代码实现。需求未实现 / 实现不符 = **bug**，最低 P1，不得归类为"建议"或"优化"
8. **禁止只查代码不查需求** — 如果有需求文档但未做 RTM 映射，审查结论无效
9. **覆盖率核算是必查项** — Phase 0 生成的待审文件清单中，每个文件必须显式标记为 `reviewed` 或 `skipped`（含具体跳过原因）。禁止静默遗漏任何文件——大 changeset 上 LLM 会"偷懒"漏审，必须用清单核算兜底（Phase 4 前置环节）
10. **禁止凭猜测编造行号** — 无法精确定位的问题按"定位失败兜底协议"处理（标注 ⚠️ 定位待确认 + 给出函数名/代码片段线索）。错误定位比无定位更有害——位置漂移会摧毁对整份报告的信任

## 执行流程

### Phase 0: 上下文理解（5 分钟）

**目标**：搞清楚"在审查什么"和"为什么写这些代码"。

```
1. 读取所有待审查的源代码文件（全量读取，不要只看 diff）
2. 读取关联的需求文档/PRD/设计文档（如有）
3. 读取关联的配置文件（application.properties 等）
4. 理解技术栈：语言、框架、依赖版本
5. 查看 git log 了解变更范围和提交历史
6. 生成待审文件清单（File Manifest）— 见下方
```

**输出**：
```
## 审查上下文
- 技术栈: [语言/框架/关键依赖]
- 变更范围: [N 个文件, M 行变更]
- 核心功能: [一句话描述这次变更做了什么]
- 关联需求: [需求文档引用]
```

#### 待审文件清单（File Manifest）

> 清单是 Phase 4 覆盖率核算的**唯一基准**，生成后不得缩水。这是防止大 changeset 漏审的硬约束。

```
生成方式：
- diff 模式：git diff --name-status <base>..<head> 列出的所有文件
  （含 Added / Modified / Deleted / Renamed，删除的文件也要审查"删除是否完整、有无残留引用"）
- 全量模式：用户指定的文件列表，或目标目录下所有源码文件
- 附加：untracked 新文件（git status 中的 ?? 条目）也必须纳入

输出格式：
| # | 文件 | 状态 | 变更行数 | 备注 |
|---|------|------|---------|------|
| 1 | src/rank.go | M | +120/-35 | 核心逻辑 |
| 2 | config.json | M | +2/-2 | 配置变更 |
```

#### 深度分析阈值（Plan Phase Threshold）

> 借鉴 OCR 的两段式审查：达到阈值时先做风险分析再主审，避免大变更"平均用力"。

满足**任一条件**时，Phase 0 必须额外输出**风险分析**（识别 2-3 个核心风险点 + 审查优先级排序），并优先深审高风险文件：
- 单文件变更 ≥ **50 行**
- 一组相关文件（同一模块/同一功能）合计变更 ≥ **100 行**

### Phase 0.5: 需求追溯矩阵（Requirement Traceability Matrix）— 必查项

**目标**：逐条对照需求原文与代码实现，找出所有"未实现"、"实现不符"、"部分实现"的条目。

> ⚠️ **这一阶段是 code review 的核心必查项，不可跳过。**
> 需求未实现 = bug，最低 P1。经验测试（API 调用、功能验证）无法替代需求追溯——
> 因为"功能跑起来了"不等于"功能做对了"。逻辑反转、条件缺失、上限遗漏等问题
> 在经验测试中表现正常（有返回、有标签、有行为），只有对照需求原文才能发现。

#### 执行步骤

```
1. 从需求文档中提取所有"可验证条目"（每个具体规则、阈值、条件、流程都是一个条目）
   - 不要只提取标题/章节，要提取到每个具体的参数值和条件分支
   - 例：需求写"T1保送，单用户单词≥3次后停止" → 这是两个独立条目：
     (a) T1层需要保送  (b) 频率限制是 per-UID×per-word, limit=3

2. 对每个条目，在代码中定位对应实现：
   - ✅ 已实现：找到代码位置，参数值/条件与需求一致
   - 🔴 不符：找到代码位置，但参数值/条件与需求不一致（如逻辑反转、阈值错误）
   - 🟡 部分：部分条件实现，部分缺失（如频率控制只有全局，缺 per-UID）
   - ⚠️ 未实现：代码中找不到对应实现

3. 对每个 🔴/🟡/⚠️ 条目，记录为 bug 候选，进入 Phase 1 问题清单
```

#### RTM 输出格式

```
## Phase 0.5: 需求追溯矩阵

| # | 需求原文 | 代码位置 | 状态 | 差异说明 |
|---|---------|---------|------|---------|
| R1 | [需求条目] | file.go:L42 | ✅ | — |
| R2 | [需求条目] | config.json:L10 | 🔴 | 需求说A，代码做B |
| R3 | [需求条目] | — | ⚠️ | 代码中未实现 |
| R4 | [需求条目] | file.go:L67 | 🟡 | 实现了X，缺Y |

### 需求符合率: X/Y = Z%
### 差距项: N个 (🔴 N1 + 🟡 N2 + ⚠️ N3)
```

#### 常见盲区（容易漏查的需求类型）

> 以下类型的需求条目在经验测试中最容易被遗漏，RTM 检查时必须重点关注：

| 需求类型 | 经验测试为什么发现不了 | RTM 检查方式 |
|---------|-------------------|------------|
| **逻辑分支条件** | 测试看到有行为就认为对，没验证是哪个分支触发的 | 逐条检查 if/else 条件是否与需求表格一一对应 |
| **频率/上限控制** | "应该有但没有"的功能，测试中无法自然触发 | 检查是否有对应的计数器/限流逻辑 |
| **维度/粒度** | 全局 vs per-UID 看起来行为一样 | 检查 Redis key/数据库索引是否包含正确维度 |
| **概率/门控** | 100%触发 vs 10%触发，测试中都能看到结果 | 检查是否有随机/采样判断逻辑 |
| **配置 vs 代码** | 配置写反了，代码忠实执行，行为"看起来正常" | 对比 Apollo/配置文件与需求原文的参数值 |
| **边界值** | 开区间 vs 闭区间在常规数据下无差异 | 检查 min_inclusive/max_inclusive 与需求括号类型 |

#### 实战教训

> 以下问题在分层治理项目 code review 中因为**没做 RTM** 而被遗漏，直到需求差距分析时才发现：

1. **T1保送策略逻辑反转**: Apollo配置 `no_click_action: promote`（零点击→保送），但需求说零点击→不干预。代码忠实执行配置，API返回看起来正常（有promote标签），但保送了错误的词。
2. **10%流量门控缺失**: 需求/开发意图是10%概率触发，代码100%触发。测试中每次调用都能看到保送效果，无法发现概率问题。
3. **频率控制缺per-UID**: 需求要求 per-UID×per-word limit=3，代码只有全局 per-word limit=30。Redis key 不含 UID，测试无法自然触发频率限制。
4. **filter 结果丢失（Go slice 传参 bug）**: void 函数 `processWeightTiered` 内部 `ret = filterLowCtr(ret, logId)` 只改局部变量。Go 的 slice 传参复制 header，调用方 `rank()` 拿到的仍是原始 slice。标记了 `Disabled=true` + `reduce_type=filter_T4` 的词仍出现在返回中。测试用例只检查 `s28d >= 900 AND c == 0`（间接推断），没有直接断言"返回结果不应包含 reduce_type 含 filter_ 的词"——导致 1.9% 泄露率未被 30 条样本检测到。

**教训：经验测试发现"有"容易，发现"错"和"缺"难。RTM 是唯一能系统发现"错"和"缺"的方法。数据流完整性审计是发现"做了但丢了"的唯一方法。**

### Phase 1: 三视角分析（Multi-Perspective Analysis）

**目标**：从三个不同视角扫描代码，尽可能多地发现问题候选。

> ⚠️ 这一阶段的输出是"问题候选清单"，不是最终结论。定级在 Phase 2/3 完成。
> ⚠️ Phase 0.5 RTM 产生的 🔴/🟡/⚠️ 条目自动进入本阶段的问题候选清单（归类为"业务正确性"）。

#### 视角 1: 业务正确性 (Business Correctness)

检查清单：
- [ ] **Phase 0.5 RTM 差距项全部已录入问题清单**（🔴/🟡/⚠️ 条目不得遗漏）
- [ ] 核心业务逻辑是否与需求文档一致（RTM 之外的补充检查）
- [ ] 边界条件处理：空值、零值、极大值、负数
- [ ] 状态流转是否完整（每个状态的入口和出口）
- [ ] 幂等性：重复调用是否安全
- [ ] 配置项与代码行为是否一致（如文档说 18:50，代码是否也是 18:50；Apollo 配置值是否与需求一致）
- [ ] 计数器/指标统计是否准确反映真实情况

#### 视角 2: 架构与并发 (Architecture & Concurrency)

检查清单：
- [ ] 线程安全：共享可变状态是否有正确的同步机制
- [ ] 资源管理：文件/连接/线程池是否在 finally 中关闭
- [ ] 异常处理：catch 块是否吞掉了不该吞的异常
- [ ] 超时与重试：外部调用是否有超时设置，重试是否合理
- [ ] 限流与熔断：高并发场景下是否有保护机制
- [ ] 死代码：是否有不再使用的分支或变量
- [ ] 日志：关键路径是否有足够日志，日志中是否泄露敏感信息
- [ ] **数据流完整性**（见下方专项）
- [ ] **语言特定反模式**（见下方专项）

#### 视角 2 补充: 数据流完整性审计（Data Flow Integrity）

> **目标**：验证集合操作（过滤、排序、转换）的结果是否真正传播到调用方。
> 这是"功能实现了但结果丢了"类 bug 的核心检查点。

**必查模式：void 函数 + 集合参数**

```
对每个 void 函数（无返回值）且接收 slice/list/array 参数的函数：

1. 函数内部是否有以下操作？
   - ret = filterFunc(ret)          ← 重新赋值
   - ret = ret[:n]                  ← 截断
   - ret = append(ret[:i], ret[i+1:]...)  ← 删除元素
   - ret = newSlice                 ← 替换为新 slice

2. 如果有 → ⚠️ 检查调用方是否能看到变更：
   - Go: slice header 是值拷贝，局部重新赋值 ≠ 调用方可见
   - Java: List 引用是值拷贝，但 list.clear() / list.removeAll() 可见
   - Python: list 引用传递，reassign 不可见但 .append()/.remove() 可见

3. 验证方法：
   - 追踪函数返回后，调用方是否对同一个变量做了后续操作（sort、truncate、return）
   - 如果调用方依赖"函数内部已过滤"的假设 → 🔴 确认是否真的可见
```

**Go 语言专项（slice pass-by-value 陷阱）：**

| 操作 | 调用方可见？ | 说明 |
|------|------------|------|
| `item.Field = value`（指针修改元素字段） | ✅ 可见 | 通过共享指针修改 |
| `sort.Slice(ret, ...)`（原地排序） | ✅ 可见 | 修改底层数组 |
| `ret = filterFunc(ret)`（重新赋值） | ❌ **不可见** | slice header 是值拷贝 |
| `ret = append(ret, item)`（可能扩容） | ❌ **不可见** | 扩容后新地址，调用方仍指旧地址 |
| `ret = ret[:n]`（截断） | ❌ **不可见** | 只改了局部 header 的 len |

> **实战教训**：分层治理项目中 `processWeightTiered` 是 void 函数，
> 内部 `ret = filterLowCtr(ret, logId)` 只改局部变量，
> 导致 6/320 个应被过滤的词泄露到 API 返回中。

**Check-then-Act 竞态检查：**

```
对每个"先检查再操作"的模式（如限流、频控、库存）：

1. 检查操作（GET/SELECT）和执行操作（SET/UPDATE/INCR）之间是否有时间窗口？
2. 时间窗口内是否有其他请求可以插入？（并发度评估）
3. 是否使用了原子操作（Lua/CAS/事务）来消除窗口？

示例（❌ 有竞态）:
  count = redis.GET(key)           ← T0: 检查
  if count < limit:                ← T1: 判断
      doPromote()                  ← T2: 执行（中间可能隔了很多逻辑）
      redis.INCR(key)              ← T3: 递增（T0~T3 之间并发可突破上限）

示例（✅ 无竞态）:
  lua_script: local c = redis.call('GET', KEYS[1])
              if tonumber(c) < tonumber(ARGV[1]) then
                  redis.call('INCR', KEYS[1])
                  return 1
              end
              return 0
```

#### 视角 3: 健壮性与可测试性 (Robustness & Testability)

检查清单：
- [ ] 外部输入校验：格式、长度、类型、范围
- [ ] 第三方依赖故障时的降级行为
- [ ] 外部 API 返回非预期格式（如 HTML 代替 JSON）时的处理
- [ ] 测试用例覆盖：核心路径、异常路径、边界条件
- [ ] 测试用例与需求文档的 TC 是否一一对应

#### 语言/文件类型特化检查表（Rule Dispatch）

> 借鉴 OCR 的规则分发引擎（按路径 glob + 文件特征将规则匹配到文件，保持模型注意力聚焦）。
> 三视角是通用扫描，本表是**按文件类型追加的特化检查**。审查每个文件时，除三视角外
> 还必须应用其对应的语言特化条目；命中多个类型时（如 `.tsx`）叠加应用。

| 文件类型 | 特化检查项 |
|---------|----------|
| **Go** | slice 传参陷阱（见专项）；nil map 写入 panic；goroutine 泄漏（无退出条件的 for/select）；defer 在循环内累积；error 被忽略或丢失包装上下文；`range` 中取地址；data race（`go test -race` 视角） |
| **Java** | NPE 路径（链式调用/Map.get 返回 null）；资源未用 try-with-resources 关闭；equals/hashCode 只实现其一；HashMap 并发写；SimpleDateFormat 共享；Spring 事务边界（自调用失效/@Transactional 不回滚场景）；Optional 误用（get 不判空） |
| **Python** | 可变默认参数（`def f(x=[])`）；浅拷贝 vs 深拷贝混淆；裸 `except:` 吞异常；`is` 比较 value；循环变量闭包捕获（late binding）；类型注解与实际不符 |
| **JS/TS** | `==` vs `===`；未 await 的 Promise（浮动 promise，错误被吞）；async 回调中异常逃逸；闭包捕获循环变量；`any` 滥用/类型断言掩盖错误；undefined 与 null 语义混淆；数组/对象共享引用的意外修改 |
| **SQL / Mapper XML** | 字符串拼接 SQL（注入）；WHERE 条件对索引列做函数/隐式类型转换（索引失效）；N+1 查询（循环内单条查询）；缺少 LIMIT 的全表查询；UPDATE/DELETE 缺 WHERE；事务边界与重试组合导致的重复执行 |
| **前端组件** | useEffect 依赖数组缺失/多余；定时器/事件监听器未清理（内存泄漏）；setState 依赖上次状态的竞态；XSS（dangerouslySetInnerHTML / v-html 注入未消毒数据）；列表 key 用 index |
| **配置文件**（properties/yaml/json/Apollo） | 配置值与需求原文逐项对照（RTM 联动）；环境差异项是否遗漏（dev/test/prod）；布尔/字符串类型混淆；默认值兜底是否存在 |
| **Shell 脚本** | 未加引号的变量（空格/通配符展开）；`set -e` 缺失导致错误继续执行；管道中 || 掩盖失败；rm -rf 路径变量为空时删除根目录 |
| **proto/接口定义** | 字段编号复用/删除后兼容性；required/optional 语义；版本兼容（新旧消费者共存） |

> **扩展原则**：遇到表中未覆盖的文件类型（如 Solidity、Terraform、K8s YAML），
> 按该类型的"运行时失败模式 + 领域安全惯例"现场构造 3-5 条特化检查项，再执行审查。

**输出格式**：
```
## Phase 1: 问题候选清单

### 业务正确性（含 Phase 0.5 RTM 差距项）
| # | 来源 | 类别 | 发现 | 位置 | 初步定级 |
|---|------|------|------|------|---------|
| B1 | RTM-R2 | bug | [需求说A，代码做B] | file.go:L42 | P1 |
| B2 | RTM-R3 | bug | [需求要求的功能未实现] | — | P1 |
| B3 | 代码检查 | bug/performance/... | [描述] | file.go:L67 | P? |

### 架构与并发
| # | 类别 | 发现 | 位置 | 初步定级 |
|---|------|------|------|---------|
| A1 | bug/performance/... | [描述] | file.java:L125 | P? |

### 健壮性与可测试性
| # | 类别 | 发现 | 位置 | 初步定级 |
|---|------|------|------|---------|
| Q1 | bug/test/... | [描述] | file.java:L200 | P? |
```

**类别（category）枚举**——每个发现必须标注，与定级正交：

| category | 含义 | 典型来源 |
|----------|------|---------|
| `bug` | 逻辑错误、行为不符预期 | 视角1 / RTM 差距 |
| `security` | 安全漏洞（注入、越权、敏感信息泄露） | 视角1/2 |
| `performance` | 性能问题（N+1、无效计算、锁竞争） | 视角2 |
| `maintainability` | 可维护性（死代码、重复、误导性命名） | 视角2 |
| `test` | 测试缺失或断言无效 | 视角3 |
| `style` / `documentation` | 风格 / 文档 | 低定级专属 |

---

### Phase 2: 定级分类 (Severity Classification)

**目标**：为每个问题候选应用严格的定级标准。

#### 定级标准（必须逐条验证）

**🔴 P0 — 阻断 (Blocking)**
> 阻断提测/发布。不修不能上线。

必须**同时满足以下全部条件**：
1. ✅ 能追踪到完整的执行路径（从入口到失败点，每一步都说得清楚）
2. ✅ 影响：数据丢失 / 安全漏洞 / 系统崩溃 / 资金损失 / 生产事故
3. ✅ 代码中**没有**其他补偿机制（如兜底逻辑、监控告警、人工干预）
4. ✅ 正常操作即可触发（不需要极端巧合或恶意构造）

**如果任何一条不满足 → 不能定为 P0。**

---

**🟡 P1 — 应修复 (Should Fix)**
> 真实 Bug 或需求不一致，应在本轮修复。

满足以下**任意一条**：
1. ✅ 能追踪到执行路径，且会产生**不正确的行为**（错误结果、误导性输出、边界场景失败）
2. ✅ 需求文档与代码行为不一致（文档说 A，代码做 B）
3. ✅ 核心路径缺少测试用例覆盖
4. ✅ 计数器/统计指标不准确，会误导运维决策

---

**🟢 P2 — 改进 (Improve)**
> 设计限制或低概率风险，排入后续迭代。

典型场景：
- 理论上的风险，但触发概率低（< 5%）或有其他机制兜底
- 设计不够优雅但功能正确
- 缺少非核心路径的测试覆盖
- 文档描述不精确但不影响理解

---

**⚪ P3 — 建议 (Nitpick)**
> 编码风格、命名、微优化。

典型场景：
- 变量命名建议
- 代码格式偏好
- 可以用更优雅的写法但不影响功能

---

### Phase 3: 定级校准 (Severity Calibration) — 核心环节

**目标**：对每个 P0 和 P1 发现进行"魔鬼代言人"式质疑。这是防止定级虚高的关键。

> **原则**：宁可放过一个 P2，不可冤枉一个 P0。如果你自己都无法说服自己"这真的会在生产中出问题"，就降级。

#### 校准问卷（每个 P0/P1 必须回答）

**Q1: 执行路径追踪**
```
请逐步追踪从用户输入/外部触发到最终失败的完整路径：
Step 1: [什么操作触发了这个路径]
Step 2: [代码执行到哪个方法]
Step 3: [什么条件导致分支走错]
Step 4: [最终产生了什么错误结果]

如果无法完成追踪 → 降级
```

**Q2: 概率评估**
```
在正常生产环境中，这个条件多久出现一次？
- 每次调用都会触发 → 概率 100%
- 特定输入才触发 → 需要说明什么样的输入，多久出现一次
- 需要多个条件同时满足 → 计算联合概率
- 需要外部系统故障 → 该系统的稳定性如何

如果概率 < 5% 且影响可恢复 → 降级
```

**Q3: 补偿机制**
```
代码中或系统架构中是否有以下机制可以兜底？
- 重试逻辑（如下次调度会修正）
- 监控告警（运维会发现并处理）
- 人工流程（如发布前的检查清单）
- 数据库约束/唯一索引
- 熔断器/限流器
- 日志中会留下明显痕迹

如果有补偿机制且影响可控 → 降级
```

**Q4: 业务影响**
```
这个问题的实际业务影响是什么？
- 用户看不到的错误（纯内部计数不准）→ 考虑降级
- 用户看到了错误但可以重试 → P1 合理
- 用户数据损坏且不可恢复 → P0 合理
- 只是日志看起来不好看 → P2/P3
```

**Q5: 最终裁决**
```
综合 Q1-Q4 的回答，维持原定级还是降级？

维持: 说明为什么这个定级是合理的
降级: 从 P? 降到 P?，原因是 [具体理由]
```

#### 校准输出格式

```
## Phase 3: 定级校准

### 校准: [问题编号] — [问题简述]
- 初步定级: P0
- 执行路径: [逐步追踪或"无法追踪"]
- 触发概率: [百分比 + 理由]
- 补偿机制: [有哪些兜底]
- 业务影响: [实际影响描述]
- 裁决: 维持 P0 / 降级为 P1 / 降级为 P2
- 理由: [一句话]
```

---

### Phase 4: 决策与报告 (Decision & Report)

**目标**：输出清晰、诚实、可操作的审查结论。

#### Phase 4 前置: 覆盖率核算（Coverage Audit）— 不可跳过

> 对照 Phase 0 的待审文件清单逐项核账。自然语言驱动的审查在大 changeset 上会"选择性失明"
> （只审了部分文件却毫无察觉），覆盖率核算是唯一兜底手段。**未完成核算，报告无效。**

```
1. 逐项核对 Phase 0 文件清单，每个文件标记：
   - ✅ reviewed — 已完成三视角 + 语言特化检查
   - ⏭️ skipped — 必须填写具体原因（自动生成代码 / 二进制 / 锁文件 / 三方库副本 / 纯文案）

2. 计算 coverage_rate = reviewed / (total - 合理跳过)

3. 输出：
   | 文件 | 状态 | 原因（skipped 必填） |
   |------|------|---------------------|
   | src/rank.go | ✅ reviewed | — |
   | pb/generated.go | ⏭️ skipped | protoc 自动生成 |

   - 覆盖率: reviewed X / 应审 Y = Z%

4. 红线：
   - 任何文件不允许无原因缺席清单
   - coverage_rate < 100% 时必须在最终报告中显式说明缺席原因
   - 核心源码文件（.go/.java/.py/.ts 等）不得以"变更太小"为由跳过
```

#### 定位失败兜底协议（Position Fallback）

> 每个问题必须给到 文件名:行号。当确实无法精确定位时，按以下流程处理，**禁止丢弃、禁止编造**：

```
1. 标注 "⚠️ 定位待确认" 前缀
2. 给出定位线索（至少两项）：
   - 函数名 / 类名 / 方法签名
   - 代码片段特征（如 "filterLowCtr 调用处"）
   - 相对位置（如 "processWeightTiered 第二个 if 分支"）
3. 在报告问题清单中单独归类，提醒人工定位后修复
4. 禁止凭模糊印象编造行号——错误定位会误导修复，且摧毁对整份报告的信任
```

#### 报告结构

```markdown
# Code Review 报告

## 审查信息
- 审查日期: [date]
- 代码版本: [branch/commit]
- 审查范围: [文件列表]
- 技术栈: [语言/框架]
- 需求文档: [引用 + 是否已做RTM]

## 需求追溯结论
- 需求条目总数: X
- 符合率: X/Y = Z%
- 差距项: N个 (详见 Phase 0.5 RTM)

## 审查覆盖率
- 覆盖率: reviewed X / 应审 Y = Z%
- 跳过文件: N个（原因见覆盖率核算表；无则写"无"）

## 提测/发布决策

[✅ 可以提测 / ⚠️ 修复 P1 后提测 / ❌ 存在 P0，阻断提测]

## 问题清单（按定级排列）

### 🔴 P0 — 阻断项 (N 个)
> 每个包含：问题描述 + [category] + 代码位置 + 执行路径 + 修复方案 + suggestion_code（修复建议代码）

### 🟡 P1 — 应修复 (N 个)
> 每个包含：问题描述 + [category] + 代码位置 + 修复方案（能给出 suggestion_code 时必须给出）

### 🟢 P2 — 改进建议 (N 个)
> 每个包含：问题描述 + [category] + 简要建议

### ⚪ P3 — 建议 (N 个)
> 一句话描述即可

### ⚠️ 定位待确认 (N 个)
> 按"定位失败兜底协议"处理的问题，含定位线索，提醒人工定位

## 已确认正确的实现
> 列出审查中发现做得好的地方，平衡批评与肯定

## 统计
- P0: X 个
- P1: X 个
- P2: X 个
- P3: X 个
- 按类别: bug X / security X / performance X / maintainability X / test X / 其他 X
- 已确认正确: X 项
```

**suggestion_code 格式**（P0/P1 必备，能构造时）：

> **修复建议代码**:
> ```go
> // 修改前 (existing_code):
> func processWeightTiered(ret []*Item) { ret = filterLowCtr(ret, logId) }
> // 修改后 (suggestion_code):
> func processWeightTiered(ret []*Item) []*Item { return filterLowCtr(ret, logId) }
> ```

展示时用"修改前/修改后"对照；修复建议必须可直接落地，禁止只说"建议重构"而不给代码。

## 常见定级陷阱 (Calibration Pitfalls)

以下是导致定级虚高的典型思维错误，审查时必须警惕：

| 陷阱 | 表现 | 纠正 |
|------|------|------|
| **理论完美主义** | "如果 API 返回非 JSON 就会崩" — 但 API 不会返回非 JSON | 追踪概率，大概率不会发生 → P2 |
| **链式灾难假设** | "A 失败导致 B 失败导致 C 失败导致全盘崩溃" — 但中间有兜底 | 追踪补偿机制 → 降级 |
| **混淆设计取舍与 Bug** | "熔断器没有恢复机制" — 但批处理下次调度会重跑 | 区分"设计可以更好"和"代码有 Bug" |
| **忽视批处理特性** | "熔断后剩余批次全部失败" — 但这是一次性任务不是常驻服务 | 考虑执行模型 |
| **过度关注极端边界** | "如果正好在 18:50:00.001 执行就会延迟 24 小时" — 调度器在凌晨 2 点跑 | 评估实际触发条件 |
| **忽略运维实践** | "如果有人在 dev 环境用生产数据" — dev 环境不会有生产数据 | 考虑实际使用场景 |

## 与三剑客技能的协作

当用户同时要求三剑客分析和 code review 时（如 "用三剑客做 code review"），按以下方式协作：

1. **三剑客负责 Phase 1**（多视角分析 + 红蓝对抗）— 挖掘问题候选
2. **本技能负责 Phase 2-4**（定级 + 校准 + 决策）— 确保定级准确

三剑客的红蓝对抗输出直接作为 Phase 1 的问题候选清单输入到 Phase 2。

---

## 适用场景

- 提测前代码审查
- 上线前最终 review
- PR/MR 审查
- 技术方案实现审查
- 代码质量定期审计
- 新成员代码入职审查

## 不适用场景

- 需求评审（用三剑客）— 但 code review 时必须拿需求文档做 RTM
- 架构方案选型（用三剑客）
- 测试用例生成（用 test-case-generator）
- 性能压测分析（用 test-result-analysis）
